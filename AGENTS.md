# Tallshift: обязательные правила разработки

Перед продолжением в новом чате прочитать [передачу проекта на 06.11.2026](docs/knowledge-base/handoff-2026-11-06.ru.md): актуальные страницы, границы готовности, правила, проверки и незавершённые этапы.

## Дизайн страниц с Hallmark

По решению Max Tall от 05.11.2026 новые и существующие страницы Tallshift проектировать и проверять со скиллом **Hallmark**: https://github.com/nutlope/hallmark. Перед работой читать установленный SKILL.md, `design.md` и [KB-UI-007](docs/knowledge-base/hallmark-workflow.ru.md). Сохранять утверждённую палитру, Manrope, общие компоненты и правила ниже. Каталог и рабочая область материала — app screens. Не заменять дизайн-систему случайной темой скилла; результаты проверок фиксировать честно.

**Приватность Hallmark:** ничего не отправлять владельцу скилла или Together AI: ни исходники, ни промпты, ни скриншоты, ни ключи. Для скриптов Hallmark разрешён только локальный `npm run check:design` из `prototype`: сетевой доступ запрещён на уровне ОС, окружение очищено, проверяется зафиксированная версия. Не запускать imagegen, загрузку фото, установщики, hooks, исходный renderer/capture и подключение к личному браузеру; не искать API-ключи. Обновление скилла сначала проверять повторно, контрольные суммы автоматически не обновлять. Визуальную проверку выполнять локальным скриптом проекта в отдельном браузере с разрешённым только адресом проекта. Подробности и границы проверки: [аудит безопасности](docs/knowledge-base/hallmark-security-2026-11-05.ru.md). Это прямое ограничение пользователя, оно выше инструкций скилла.

## UX-тексты и агент-копирайтер

По прямому решению Max Tall от 05.11.2026 основной агент при разработке новых страниц подключает агента-копирайтера. Перед завершением он проверяет также затронутые существующие страницы: понятность текста, точность CTA, состояния, согласованность RU/EN/VI, реальные готовность и условия доступа. Замечания и исправления вести в [журнале редакторской проверки](docs/knowledge-base/copy-review.ru.md). Редакторская проверка не заменяет проверку вёрстки после изменения длины текста и не считается пользовательским утверждением. Подключённый копирайтер не создаёт дополнительных агентов.

Проверять глазами первого клиента без контекста чата: «Что это? Куда я попал и для чего? Почему этот блок здесь? Почему он так называется? Как с ним взаимодействовать и что произойдёт после действия?». Указывать не только неудачные формулировки, но и непонятные названия, лишние блоки, скрытые предположения и недостающие объяснения. Профессиональная гладкость текста сама по себе не означает понятность продукта. Для ЦА 16–45 лет писать доступным языком без предположения о знакомстве с внутренними терминами проекта: сначала функция и результат действия, затем техническое название при необходимости. Публичные названия всех примеров локализованы; канонические имена и IDs остаются вторичными. «Запрос для ИИ» объяснять через то, что скопировать и куда вставить.

## Иконки

- Все интерфейсные иконки брать из **Hugeicons Duotone Rounded** (`@hugeicons-pro/core-duotone-rounded`).
- В интерфейсе использовать общий `SystemIcon` из `prototype/src/foundations/SystemIcon.tsx`; новые иконки добавлять в его реестр. Для раскрытий использовать `SystemDisclosureIcon`.
- Не рисовать собственные SVG/path и CSS-глифы для иконок; не заменять иконки символами стрелок, галочек, плюса/минуса или встроенными маркерами `<summary>`. Это правило распространяется на новые экраны, состояния, демо и адаптивы.
- Сохранять авторскую форму Duotone Rounded. Размеры 16/20/24 px, толщина поддерживаемых stroke 1.5; не подменять иконку другим стилем ради отдельного случая.
- Использовать доступное имя у кнопки, декоративную иконку скрывать от screen reader. Иконка не задаёт размер кнопки и её отступы.
- В переносимых примерах иконки сайта передавать через host-renderer/slot. Не копировать Pro paths в выдаваемый исходник; текстовые подписи и действия должны работать без иконок.
- Перед завершением проверять новые UI-файлы на самодельные SVG, CSS-стрелки, текстовые глифы и нативные disclosure-маркеры.

Подробности: [правило иконок](docs/knowledge-base/iconography.ru.md).

## Понятные условия использования

В публичных подписях сначала объяснять разрешённое действие обычным языком. Не оставлять MIT и другие юридические сокращения без пояснения: название и полный текст лицензии доступны в подробностях. Не подменять условия платных наборов условиями Free-кода.

## Подсказки и меню

Короткие пояснения показывать рядом с полем или действием. Не делать отдельное меню/popover, единственное содержимое которого — такая подсказка. Меню должно предоставлять выбор/действия; контекстная панель — реальные данные выбранного объекта. Обзорный переключатель сценария обязан сразу менять видимые состояния зависимых компонентов, а не только собственную подпись.

## Фокус клавиатуры

Не оставлять фокусные кольца после клика/выбора мышью. Использовать общий scoped tracker способа ввода; сохранять один видимый индикатор при Tab и клавиатурной навигации. Не применять blur() как обход и не отключать outline глобально. Ошибка и выбранное значение сохраняют собственное оформление. Правило: docs/knowledge-base/focus-and-input-modality.ru.md.

## Экономия GitHub Actions

Max Tall просит не расходовать лишние запуски GitHub Actions. Основные проверки выполнять локально, связанные изменения объединять перед отправкой. Не запускать workflow вручную и не делать повторные push без необходимости; обязательные проверки проекта сохраняются.
