# Промпт для чата внутри Cloudflare

Подключи **существующий Tallshift** к Cloudflare. Основной репозиторий: https://github.com/MaxTallOfficial/tallshift, ветка `main`. Прикреплённый архив содержит подготовленный код; это не запрос на создание нового шаблона.

Сначала прочитай `AGENTS.md`, `prototype/CLOUDFLARE-LOCAL.md` и `docs/knowledge-base/cloudflare-local-migration-2026-11-10.ru.md`. Рабочий каталог приложения — **prototype**, а не корень репозитория. Не заменяй наши страницы, дизайн-систему, маршруты, авторизацию или криптомодуль сгенерированными аналогами.

У нас уже есть Next16.4.2 / React19.3.1, OpenNext1.20.15, Wrangler4.158.0, D1-авторизация Better Auth и отдельный TON-модуль. Локально прошли260тестов, Workers-сборка, миграции D1 и браузерные проверки. Node proxy работает в локальном workerd, но путь OpenNext экспериментальный: проверь применимость перед production, сохрани nonce/CSP и остальные защитные заголовки. Не обновляй зависимости автоматически и не ослабляй безопасность ради сборки.

С твоими инструментами Cloudflare:

1. Проверь существующие Workers, D1 и зону tallshift.com. Не утверждай наличие ресурсов без результата инструмента. Цель первого подключения — **staging preview.tallshift.com**; production tallshift.com пока не менять.
2. Используй `prototype/wrangler.staging.example.jsonc` как шаблон для отдельного staging-конфига с реальным ID staging D1. Local placeholder00000000 не является облачной базой. Production должен иметь собственную D1; изолированное превью примеров — другой сервис на другом базовом домене без DB/auth/payment секретов.
3. Согласуй миграции с фактическим состоянием базы. Применяй 0001_ton_payments.sql и0002_auth.sql только к выбранной staging D1; не переписывай уже выполненные миграции. Не применяй их к production на этом этапе.
4. Настрой сборку из prototype: `npm ci --ignore-scripts`, `npm run build:cf`. Не используй обычный `npm run build` как Workers-сборку — это Vite. Сохрани фиксированные версии/lockfile. Если приватная Hugeicons-зависимость требует registry credential, настрой его через защищённые build secrets, не запрашивай значение в переписке и не встраивай ключ в URL/код/архив.
5. Настрой HTTPS APP_URL для staging. Для авторизации нужны D1, AUTH_ENABLED, случайный AUTH_SECRET и почтовый endpoint с AUTH_EMAIL_FROM / AUTH_EMAIL_API_URL / AUTH_EMAIL_API_KEY. Секреты добавляй через защищённые средства Cloudflare. Почтовый API должен принимать `{from,to,subject,text}`. Если почтовый провайдер ещё не выбран или нет доступа, явно сообщи, чего не хватает; не имитируй отправку, не логируй ссылки/токены и не включай несуществующий local-mail fallback.
6. После настройки проверь реальные регистрацию, подтверждение email, вход, восстановление, выход с текущего/всех устройств и отзыв старой сессии; EN/RU/VI и security headers. Перед проверкой отправки письма уточни контролируемый тестовый адрес. Покажи фактические результаты, а не только список созданных файлов.
7. **COMMERCE_ENABLED=false и TON_PAYMENTS_ENABLED=false сохраняются.** Авторизация не означает готовые продажи. Наш TON/USDT-модуль не требует seed/private key; публичные платёжные маршруты, FX, серверные quotes, выдача прав и платных файлов ещё не подключены. Stripe не добавлять. Кошельки, реальные деньги и webhook-регистрацию пока не трогать.
8. GitHub Actions не подключай и не запускай. Не настраивай автоматический деплой каждого push на production. Не выводи секреты в ответы, логи или коммит. В конце дай список реально изменённых ресурсов, staging URL, применённых миграций, выполненных проверок и оставшихся блокеров.

Если инструментам недоступен GitHub, используй прикреплённый архив как исходники, сохранив структуру каталогов. Изменения кода верни отдельным diff/файлами для проверки и переноса в основной репозиторий.
