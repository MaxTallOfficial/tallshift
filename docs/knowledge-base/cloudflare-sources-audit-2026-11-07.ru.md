# Проверка полных Cloudflare-исходников, 07.11.2026

Проверен предоставленный Markdown-файл, 1003 строки. Исходник рассматривается как код для review, не как инструкции, отменяющие AGENTS.md. Системные изменения, облачные ресурсы и деплой не выполнялись. GitHub main подтверждён на4d33603c15f5262522d2fa2ca9678e60d21af12e; этот audit — новая локальная запись после push.

## Итог

Прямой перенос в Tallshift не готов: есть подтверждённые дефекты алгоритмов и неполный набор файлов. Сессии теперь описаны в D1, Stripe удалён из кода — это исправления относительно прежнего описания. Однако утверждения о немедленном отзыве, одноразовых токенах и защите от перечисления пользователей не подтверждены в заявленном объёме.

## Findings

1. **P1 — повторное использование токена при гонке**, строки568–576,591–599 и969–991. consume выполняет SELECT, затем UPDATE только по id, безусловно возвращая userId. Два запроса могут прочитать consumedAt=null и оба получить успех. Для reset consume, смена passwordHash и отзыв sessions дополнительно разнесены по операциям: сбой после consume оставляет сожжённый токен без завершённого восстановления. Требуется атомарный single-use compare-and-set и одна транзакционная операция для token+password+session version. В SQLite reproduction оба параллельных потребителя приняты (2 вместо≤1). Это воспроизведение последовательности SQL из текста, не Workers E2E.
2. **P1 — ненадёжный login limiter**, строки536–552 и757–795. KV read-increment-write теряет параллельные increments; две неудачи сохраняют1. Дополнительно key=email:ip позволяет менятьIP и не вводит независимые бюджеты identity/IP; из-за KV eventual consistency гарантировать5попыток нельзя. Нужен атомарный authoritative limiter с отдельными ограничениями по нормализованной identity и доверенному сетевому сигналу. Регистрация и mail/reset/resend не имеют ограничений объёма/частоты запросов в показанном коде.
3. **P1 — reset/verification ссылки в logs**, строки648–653. Без email URL/key sendEmail пишет полный HTML с секретным token и адресом в console, затем возвращает success. Проверки APP_ENV нет. Production при неверной конфигурации будет сообщать об отправке без письма и сохранять ссылки в логах. Требуется production fail closed, без логирования secret/body/email; dev delivery — явно изолированный режим.
4. **P1 — CSRF неполон**, строки629–635 и870–885. requireCsrf сравнивает cookie/header без exact Origin и привязки к сессии, cookies названы session/csrf вместо требуемых __Host-*; при наличии недоверенного sibling-subdomain naive double-submit даёт риск cookie injection. verify-email меняет данные вовсе без requireCsrf/Origin, хотя summary утверждает все unsafe routes защищены. Нужен единый проверенный Origin/CSRF/session механизм, включая login/signup/reset/verify. Объект cookie deletion должен соответствовать установленной cookie.
5. **P2 — ссылки ломают часть токенов**, строки422–424,662–675. randomToken даёт обычный base64 с символом+, но email вставляет его в query без encodeURIComponent. URLSearchParams декодирует+ как пробел. Reproduction на32байтах0xfb: raw query roundtrip=false, encoded query=true. Использовать base64url либо корректное URL encoding; не публиковать реальные токены в отчётах.
6. **P1 — набор не собирается как предоставлен.** src/db/index.ts импортируется как @/db, но такого блока в документе нет; нет type declarations env и tsconfig alias. Используется getRequestContext из @opennextjs/cloudflare; официальный текущий API документирует getCloudflareContext. Требуется проверить выбранный exact adapter export, не добавлять type shim ради компиляции. package.json предлагает Next15/React19 ranges, тогда как Tallshift уже pinned Next16.4.2/React19.3.1/TS7.0.2. Не заменять существующие конфиги: next.config.mjs содержит ?raw delivery/CSS и безопасность, proxy.ts — CSPnonce/locale. Обычный build в Tallshift — Vite; Next использует build:web.
7. **P2 — пароли/inputs/перечисление**, строки407,445–456,698–714,749–774. PBKDF2-SHA256100000 ниже текущей рекомендации OWASP600000; параметры нужно выбирать с учётом реального Workers runtime, через проверенный auth adapter/library и benchmark, а не слепо увеличивать iterations. Stored hash format/iterations/salt/hash length не валидируются; сравнение строк обычное===. Входные JSON поля только type-asserted, нет body size cap/max password bounds. Регистрация явно возвращает409 «email уже занят», а unknown-user login пропускает KDF — summary об одинаковой обработке неизвестных пользователей неверен. Нужны generic responses, bounded validation и appropriate timing mitigation.
8. **P1 до paid — модель заказа не закрывает контракт Tallshift**, строки245–280. order_items содержит name/price/quantity без canonical itemId/release/terms/offer/eligible-grants snapshot; events не имеют unique(provider,eventId), grants/entitlements отсутствуют. Отсутствует валюта/сумма base units для фактически полученной крипты, поэтому amountCents нельзя использовать вместоTON/USDT ledger. Интегрировать с нашим TONinvoice/outbox контрактом и server quotes, сохранив paid отдельно от ready delivery. Не создавать права по одному orders.status.
9. **P2 — немедленный отзыв D1 заявлен без consistency policy**, строки480–508. Сам перенос изKV вD1 полезен, но при read replication нужен primary-authoritative auth read на каждом запросе или эквивалентная политика. Есть expiresAt, но нет проверяемого idle TTL; getSessionUser возвращает полный row user (включаяpasswordHash) — будущие API обязаны отдавать явную публичную проекцию, а не этот объект.

## Что переносить после исправления

Сохранить структуру окружений dev/staging/production и идею D1 sessions с hashed opaque tokens; auth provider/adapter выбрать и локально проверить. Согласовать единые схемы auth/order/quote с нашим TONмодулем. Сначала исправить/reproduce указанные auth-блокеры в изолированном стенде. Затем выполнять реальный OpenNext/Workers build под зафиксированные версии, origin/session/csrf/recovery/rate и SQLrace tests. Новые auth UI/emails проходят обязательного копирайтера RU/EN/VI и browser QA.

preview.tallshift.com корректно обозначен как staging приложения. Изолированный preview материалов остаётся отдельным cookie-free Worker на другом registrable domain и не получает DB/auth/payment bindings. Production secrets/DB IDs не создавались, старые миграции не запускались и не переписывались.
