# Cloudflare: проверка описания внешнего шаблона, 07.11.2026

## Статус и разделение работы

Max Tall попросил одного агента вести весь криптомодуль, а основного агента — помочь с Cloudflare, авторизацией и заказами. Криптомодулем владеет ton_payment_review; другие агенты по крипто остановлены/завершены. Внешний шаблон генерируется другой нейросетью и пока не перенесён в постоянный репозиторий. Получено описание файлов, но не их исходники. Проверка ниже — сопоставление описания с ТЗ, не аудит реализации и не результат деплоя.

Описание экспорта: Next.js App Router, D1/Drizzle users/orders/order_items/payments, собственный PBKDF2 auth, sessions в KV с TTL30d, Stripe webhook, staging preview.tallshift.com, production tallshift.com. Конкретный runtime, параметры PBKDF2, CSRF, email verification/recovery, revocation, SQL invariants и конфигурация сборки неизвестны до чтения кода. Нельзя утверждать наличие уязвимости только по отсутствию детали в описании.

## Что требуется согласовать перед переносом

1. Источник истины — существующий MaxTallOfficial/tallshift. Next-приложение сейчас расположено в prototype/app, package/lockfile/Next config в prototype. Не заменять корень проекта файлами отдельного стартового шаблона: сохранить страницы, общую дизайн-систему, локализации, переносимые примеры и историю. Файлы шаблона сначала читаются отдельно, переносятся выборочно.
2. Stripe пользователь не выбирал. Текущий платёжный scope — TON и USDT в сети TON, отдельный агент готовит серверный модуль. Обобщённые orders/payments не привязывать обязательными полями к Stripe; nullable provider refs и отдельный adapter допускают дальнейшее подключение. Stripe credentials не требуются для локального запуска/авторизации и до выбора провайдера должны оставаться неактивными.
3. Сессии обязаны соответствовать инженерному контракту: opaque server-side, __Host-* Secure/HttpOnly/SameSite=Lax без Domain, server rotation, revoke current/all/deletion, TTL+idle policy, CSRF+exactOrigin, проверенная identity, recovery, reauth sensitive actions. KV-only cache не даёт гарантии немедленного отзыва в других регионах. Нужен authoritative check с согласованностью, например primary D1; KV можно оставить необязательным вспомогательным хранилищем. Если используется D1 read replication, нельзя переносить тот же stale-read дефект туда: критичные auth/revoke проверки требуют primary/надлежащей consistency policy.
4. Самописный PBKDF2 не объявляется безопасным или небезопасным без исходников. Предпочтение проекта — проверенная auth-библиотека/провайдер через adapter. Для рассмотрения есть Better Auth с Drizzle/D1; конкретный package/version/config пока не выбран и не утверждён. При review проверить salt/randomness/iterations, constant-time compare, account enumeration, email verification/recovery, throttling, single-use expiring tokens и revoke sessions. Создание users через демонстрационный публичный POST /api/users не является signup flow.
5. preview.tallshift.com может быть staging основного приложения. Изолированное демо-превью — отдельный Worker/site на другом registrable domain, без DB/auth/payment secrets/cookies. Не смешивать эти назначения. Для staging, development и production явно определить bindings/credential/cookie boundaries; paid production данные не попадают в тестовые окружения.
6. Наличие nodejs_compat не доказывает совместимость Next. Проверить выбранный Workers adapter, точные lockfile версии, Webpack ?raw/source exports, CSS Modules, server/client boundary, реальный Workers build/run, CSP nonce/proxy и redirects. Наша Node Next production сборка/consumer fixtures не равны Workers runtime evidence. Не менять Next/React версии или framework на другой автоматически ради шаблона.
7. Миграции добавлять согласованно. Существующий выполненный 0001_init не переписывать; crypto migration пока локальная 0001_ton_payments.sql — перед применением общего набора проверить порядок/идентификаторы и отсутствие конфликтов. Production миграции ещё не запускались.
8. Авторизация не открывает продажи автоматически. Quote формируется только сервером из verified ownership/receipts, получает user/offer/policy snapshot и срок; paid определяется серверной сверкой, grant/delivery выполняются идемпотентно. Не покупать неготовые платные файлы. Free остаётся доступным без аккаунта. Серверные auth/DB/payment endpoints по умолчанию fail closed, существующий checkout пока расчёт.
9. Локальные проверки первичны. GitHub Actions, автоматические deploy builds и платные ресурсы не включать без необходимости; один согласованный перенос вместо нескольких push/workflows.
