# Коммерция: сервер выдачи, учёт прав и сверка оплат · 26.11.2026

Направление 2 из трёх параллельных сессий (поручение Max Tall от 26.11.2026). Роль — `platform-engineer`, ревью — независимый `qa-engineer`. Это **локальная серверная подготовка**, не запуск продаж. Облако, флаги, секреты, миграции на staging/production, R2 и cron не трогались. Деньги не принимались, транзакций не было.

Список решений для запуска, отправленный Max Tall: [commerce-launch-decisions-2026-11-26.ru.md](commerce-launch-decisions-2026-11-26.ru.md).

## Реализовано (локально, в ветке `claude/commerce-server-4b6dc3`)

**Учёт прав на сервере вместо localStorage.** Additive-миграция `prototype/migrations/0004_commerce_fulfillment.sql`: `commerce_receipts`, `commerce_grants`, `commerce_fulfillments`, `commerce_release_revocations`, `commerce_download_events`, `ton_scan_cursors`. SQL-триггеры: receipt только для оплаченного заказа, чей оплаченный счёт совпадает с неизменяемым quote; grant только при этом receipt и только на позицию и релиз из оплаченного snapshot; receipt и grant неизменяемы и не удаляются; отозванный grant не активируется снова; отзыв релиза окончательный; курсор сканера движется только вперёд. Ручного `paid=true` по-прежнему нет: триггер 0003 не даёт пометить заказ оплаченным без проверенного счёта.

**Идемпотентная выдача (fulfillment).** `src/server/orders/fulfillment.ts` и `ledger.ts`. Подтверждённое намерение из `ton_payment_outbox` одним D1 batch превращается в оплаченный заказ, receipt, grants на оплаченные missing ID (распределение суммы по контракту: $23 на 17 ID = 5×$1.36 + 12×$1.35), состояние `fulfilled`, закрытое намерение и `delivery_state='delivered'` у счёта. Повтор и параллельные воркеры ничего не дублируют. Сбой внутри batch откатывает всё и повторяется с backoff 60 с → 1 ч, максимум 8 попыток, затем `review`. Несовпадение счёта и quote или неизвестный релиз — сразу `review`, без grants. Повторная покупка уже принадлежащего выдаётся, но помечается `OWNERSHIP_OVERLAP` для поддержки. Окно обновлений — 12 календарных месяцев UTC от оплаты с поправкой на конец месяца и 29 февраля. «Оплачено» и «выдано» разделены: статус заказа `deliveryStatus` = `not_ready` / `pending` / `fulfilled` / `review`.

**Авторитетные ownership и receipts.** `ledger.pricingOwnership()` берёт активные grants и одну подходящую оплату Product (paid или частично возвращённая, за вычетом возврата, не больше $16; disputed/refunded не учитываются, суммы не складываются). Сервис quote берёт ownership только отсюда. `GET /api/v1/me/entitlements` отдаёт позиции, дату окончания обновлений (включительно, UTC), релизы с доступом и receipts владельца.

**Приватное хранилище и выдача.** `src/server/delivery/`:
- `releases.ts` — серверный реестр релизов (пустой: все 23 платные позиции planned) с проверкой формата, размера ≤ 5 MiB и ключа объекта; покрытие = купленный релиз, релизы до конца окна, исправления безопасности для владельцев; отозванный релиз не выдаётся.
- `storage.ts` — адаптер приватного R2 (binding `PAID_ARTIFACTS`): ключ только из реестра; размер и SHA-256 проверяются до отдачи первого байта.
- `tickets.ts` — короткоживущий (120 с) HMAC-билет. Ключ выводится из `AUTH_SECRET` с отдельной меткой, нового секрета не нужно. Билет несёт только digest пары (пользователь, сессия), позицию, хеш релиза, срок и nonce; внутренних ID в URL нет.
- `downloads.ts` — `POST /api/v1/downloads` (Origin, сессия, CSRF, лимит, строгий JSON) выдаёт билет; `GET /api/v1/downloads/{ticket}` требует ту же живую сессию и заново проверяет права и отзыв релиза при каждом запросе. Ответ `private, no-store`, `attachment`, `nosniff`, `CSP: default-src 'none'; sandbox`. Отказ хранилища, базы или авторизации — 503 без байтов, владение не удаляется. Так совмещены требование ТЗ «без публичной подписанной ссылки» и требование задачи «подписанная короткоживущая ссылка, привязанная к владельцу».

**FX-интерфейс.** `src/server/payments/fx.ts`: провайдер возвращает цену и собственное время котировки; шлюз проверяет свежесть (≤ 60 с), будущие метки времени, формат, нулевые значения, требуемое число источников и расхождение с перекрёстным источником. В счёт сохраняются источник, `quotedAt` и `expiresAt`. Встроенного провайдера, фиксированного курса и USDT = $1 нет: без утверждённого провайдера счёт не создаётся (`FX_NOT_CONFIGURED`).

**Вебхук — только подсказка, плюс cron с курсором и backfill.** `ton/hints.ts` даёт вебхуку TonAPI и сканеру один ключ подсказки, поэтому они дедуплицируют друг друга. `ton/scanner.ts` пишет подсказки для завершённых транзакций и сдвигает сохранённый курсор в том же D1 batch, только по непрерывному завершённому префиксу; незавершённая транзакция не пропускается. Аренда защищает от параллельных сканеров. Без курсора сканер стартует с головы аккаунта, только если ни одна транзакция после существующего счёта не может быть пропущена; иначе нужен явный `initialize(lt)` оператором. `backfill(from,to)` перечитывает закрытый диапазон, не двигая курсор. `orders/schedule.ts`: скан → существующий inbox worker → fulfillment; каждый шаг изолирован, в отчёте только счётчики и коды. Пока счетов нет и продажи выключены, сеть не опрашивается.

**Host и публичные маршруты за флагами.** `orders/host.ts`, `routes.ts`, `launch.ts`, `flags.ts`, маршруты `prototype/app/api/v1/**`: quote, счёт TON, статус заказа и счёта, entitlements, выдача билета и скачивание, вебхук TonAPI. Флаги проверяются **до обращения к D1**: при выключенных `COMMERCE_ENABLED`/`TON_PAYMENTS_ENABLED` (продажи) и `COMMERCE_DELIVERY_ENABLED` (выдача) все маршруты отвечают `503 COMMERCE_DISABLED`; в production таблиц 0003/0004 нет, и они не нужны. Выдача имеет отдельный флаг: экстренная остановка продаж не блокирует скачивание уже купленного. Статус заказа и счёта читается при любом включённом флаге. Даже при включённых флагах продажи закрыты, пока в `launch.ts` нет утверждённых terms, налога и FX, а реестр релизов пуст. Вебхук работает только с секретом `TONAPI_WEBHOOK_SECRET` и не зависит от флагов продаж. `src/server/cloudflare/worker-entry.ts` — необязательная точка входа Worker с `scheduled()` по схеме OpenNext custom worker; реальные `wrangler.staging.jsonc` и `wrangler.production.jsonc` её не используют.

**Шаблоны.** `wrangler.*.example.jsonc` описывают порядок включения (миграции → приватный R2 → cron → секреты → флаги), каждое действие — с отдельного «да». Реальные staging/production-конфиги не изменены. CSP, nonces и заголовки не менялись, зависимости не обновлялись.

## Не проверено

- Настоящий Workers/D1 E2E: миграция 0004 не применялась ни к одной облачной базе; поведение `json_each`, триггеров и batch проверено только на SQLite (`node:sqlite`) через фасад D1.
- Реальный R2, реальный cron trigger, реальная доставка вебхука TonAPI, реальные ответы Toncenter для `head()` и `scan()`: формат синтетический, по существующему адаптеру.
- Живая покупка, testnet-оплата, возвраты: не выполнялись и в этом этапе запрещены.
- Checkout UI не делался (нужны дизайнер и копирайтер после готовности сервера).
- Одновременные потоки скачивания (≤ 3 на пользователя по ТЗ) не ограничены; лимит есть только по частоте (≤ 30 в минуту).

1. Решения Max Tall из списка: продавец и условия, налоги, FX-провайдер, хранилище, возвраты, первый набор, кошелёк получения.
2. Готовые проверенные ZIP первого набора → запись в `paidReleaseRegistry` → загрузка в приватный R2.
3. С отдельного «да», сначала staging: миграции 0003+0004, R2 binding, custom worker + cron, секреты, `AUTH_ENABLED` на staging (сейчас `false`), затем флаги.
4. Настоящий E2E на staging (testnet или согласованная маленькая оплата), затем checkout UI RU/EN/VI с дизайнером и копирайтером.
5. Процедура оператора для `review`, возвратов и отзыва релиза (методы есть только на уровне store, маршрутов нет).
