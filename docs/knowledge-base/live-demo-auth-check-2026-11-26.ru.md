## Задача А. Интерактивные демо

### Как проверялось

Скрипт `prototype/scripts/verify-live-demos.mjs` с драйвером `prototype/scripts/cdp-lite.mjs`. Установленный Chrome 158 запускается в headless-режиме с временным профилем; управление — через DevTools Protocol, без npm-зависимостей. Сценарий только читает: открывает страницы, нажимает элементы внутри демо и меняет настройки страницы, которые хранятся в браузере. Входа в аккаунт, отправки форм и запросов к API аккаунта нет.

```sh
cd prototype
node scripts/verify-live-demos.mjs --env production,staging --out <папка>
node scripts/verify-live-demos.mjs --env production,staging --widths 375 --items A001 --slow --out <папка>
```

На каждой из 120 страниц (`/{locale}` и `/{locale}/library/{slug}`) проверяется:

- iframe загружается со своего демо-сервера (`tallshift-demo…` для production, `tallshift-demo-staging…` для staging) с `sandbox="allow-scripts allow-same-origin"`;
- мост подтверждает применение настроек: статус под превью очищается после ответа `APPLIED`;
- язык демо совпадает с языком страницы;
- в демо нет ошибки рендера и горизонтального переполнения, как и на странице;
- взаимодействие: настоящий клик (на 375 px — касание) по первому элементу демо, который меняет его состояние;
- настройки (только на страницах примеров): новый цвет `#A8D8FF` через поле и Enter; движение «Выкл.» через переключатель. На 375 px настройки открываются в нижней панели;
- высота iframe совпадает с высотой содержимого, когда демо на экране;
- на главной и странице C001: «320 px» сужает превью, «Загрузить снова» перезапускает его;
- консоль, исключения, проблемы DevTools, нарушения CSP, ошибки HTTP и запросы к посторонним хостам — и на странице, и внутри iframe;
- в прогоне 2 добавлено: слова подписей кнопок, ссылок, вкладок и заголовков внутри демо не разрываются между строками.

### Исправление: реализовано, проверено локально, не задеплоено

Иначе SSR и первый рендер показывают панель превью со статусом «Загружаем превью…». iframe появляется после гидрации: канал случайный для каждого монтирования. Мост postMessage, `preview-protocol`, `deployment-policy`, демо-сборка и тексты не менялись.
- Тест `prototype/tests/remote-preview-ssr.test.ts` (3 случая):
  - SSR с адресом: «Загружаем превью…» на RU/EN/VI, без заглушки и без iframe;
  - пустой адрес, адрес с путём или логином, `javascript:`, `ftp:`: честная заглушка;
  - выбор origin, включая совпадение с адресом сайта.

  На старом коде SSR с заданным адресом выдаёт заглушку, это проверено.

### Замечания вне демо: не исправлялись

1. **Cloudflare Web Analytics включена на обоих сайтах.** Cloudflare сам вставляет в HTML скрипт `static.cloudflareinsights.com/beacon.min.js` с nonce страницы и отправляет данные на `/cdn-cgi/rum`. В коде проекта этого нет; это настройка зоны. CSP не нарушается. Решение за Max Tall: оставить и упомянуть в условиях и приватности или выключить.
2. **Staging: `/api/auth/get-session` → 503 `AUTH_UNAVAILABLE`.** Ошибка попадает в консоль на каждой странице. Авторизация на staging выключена намеренно, но клиент запрашивает сессию, не глядя на `readiness`. Зона платформы/авторизации.
3. **Главная после гидрации.** На медленной сети SSR-контент приходит частично без стилей, затем на ~0,5 с заменяется экраном «Загружаем страницу…» и появляется снова. Это ленивые страницы приложения, а не превью; зона фронтенда. Исправление заглушки этого не меняет.
4. **Скачок высоты демо на телефоне.** iframe начинает с 440 px. Пока демо за пределами экрана, Chrome не отрисовывает iframe с другого сайта, поэтому сообщение `RESIZE` приходит, только когда пользователь до него докрутит. Тогда содержимое ниже сдвигается; например, у A006 440 → 861 px. Мост по условиям задачи не менялся.
5. **Проблема DevTools «FormEmptyIdAndNameAttributesForInputError».** Числовое поле длительности (`SystemDurationControl`) без `id` и `name`; встречается на каждой странице примера. Это подсказка для автозаполнения, не ошибка. Зона общих компонентов.
6. В Next-приложении нет `<noscript>`. Без JavaScript сайт показывает SSR-разметку с неработающими элементами управления.
7. `Permissions-Policy` формируется дважды: в `next.config.mjs` и в `proxy.ts`. Ответ содержит повторы `camera=()`, `microphone=()` и других с одинаковыми значениями. Вреда нет, это чистка.

### Ошибки в самих примерах

**A001 — подпись главной кнопки рвётся по слогам.** Дефект нашёл `user-critic` (отчёт `docs/reviews/user-critic-2026-11-26.ru.md` в ветке `claude/user-critic-066247`). Здесь он подтверждён замером на живых сайтах:

- на всех 24 страницах с A001 (главная и страница примера, оба сайта, RU/EN/VI, 1440/375) слова подписей занимают по 2–6 строк. Примеры: «Скопировать» — 6 строк, «Copying…» — 4–5, «Sao chép» — по 2;
- снимок: [a001-label-split-prod-en-1440.png](evidence/live-demo-auth-check-2026-11-26/a001-label-split-prod-en-1440.png).

Причина в CSS примера: `.buttonContent` в `prototype/src/study/AfterlightExample.module.css` всегда резервирует первую колонку 37 px (30 px на узких экранах) под иконку. Демо-сервер не передаёт `renderStateIcon`, поэтому подпись попадает в эту колонку. В выдаваемом коде иконки тоже необязательны: инструкция A001 (`src/study/recipe.ts`) обещает, что «текстовые состояния и действия работают без иконок». Значит, пользователь по умолчанию получит ту же сломанную раскладку.

Чинить это в превью-сборке подстановкой иконок нельзя: демо разойдётся с выдаваемым кодом. Исправление — в рецепте, зона сессии рецептов.

Других дефектов в примерах не найдено. Все восемь примеров с элементами управления реагировали на клик; исключений и ошибок рендера внутри демо нет. У S002 элементов управления нет по замыслу примера.

### Не проверялось

- Ширины 320, 768 и 1024 px; клавиатура внутри iframe; `prefers-reduced-motion`; forced colors; экранные дикторы.
- Визуальное качество каждого примера: проверялись функции; глазами просмотрены только снимки главной.
- Настройка «Длительность»: проверялись только цвет и движение.

- Исправление на живых сайтах: нужен деплой.

- вход, письма, выход с одного и со всех устройств и сброс пароля работают на production с 10.11 и открыты любому посетителю;
- покупок и скачиваний (SALE-10), удаления аккаунта (BETA-13) и страницы о данных (BETA-09) нет;
- в предложенном roadmap для беты нужно условие G1.11 (страница о данных и удаление аккаунта или временно выключенный вход — вопрос 1). Проверка входа там стоит в W1, и roadmap советует начать с контролируемой регистрации, чтобы увидеть возможное превышение лимита CPU при хешировании пароля.

Рекомендация была проверить уже открытую регистрацию сейчас; если вход решат временно выключить — проверить перед повторным включением, сначала на staging. Max Tall выбрал «Отложить».

Пока регистрация открыта, остаётся непроверенным, работают ли у посетителей письмо, подтверждение, отзыв сессий и сброс пароля. Также не выяснено, укладывается ли хеширование пароля в лимит CPU Workers.

Для продолжения было подготовлено и затем остановлено:

- `wrangler tail tallshift` с фильтром, который убирает строку запроса;
- SELECT по трём адресам (в 14:02 и 14:50 UTC их в базе не было);
- страница регистрации во встроенном браузере без активной сессии.

План ниже остаётся в силе.

Проверено только чтением:

- `GET /api/auth/readiness`: production — `{"enabled":true,"emailReady":true}`, staging — `{"enabled":false,"emailReady":false}`;
- `GET /api/auth/get-session`: production без cookie — `200 null`, staging — `503 AUTH_UNAVAILABLE`;
- экраны регистрации, входа, восстановления, нового пароля, подтверждения почты и кабинет на production: 6 экранов × RU/EN/VI × 1440/375 = 36 открытий. Поля ввода ничем не заполнялись, формы не отправлялись. Все экраны открылись с заголовком, полями (`email`, `new-password`, `current-password`) и кнопкой действия. Ошибок консоли и переполнения нет. Подсказки DevTools о полях без `id`/`name` на этих экранах не собирались. Подтверждение почты и новый пароль без ссылки сразу честно сообщают «Ссылка недействительна, устарела или уже использована…».

### План проведения (когда Max Tall решит продолжать)

Пароль Max Tall вводит сам, письма открывает тоже сам. Я веду по шагам и сверяю три источника:

- ответы API во встроенном браузере;
- `wrangler tail tallshift` через фильтр, который убирает строку запроса со ссылками и токенами;
- SELECT в `tallshift-db-prod` только по тестовым адресам: подтверждение, `auth_version`, число сессий, использованные ссылки, время смены пароля. Хэши и токены не выбираются.

| # | Шаг | Ожидаемый результат |
| --- | --- | --- |
| 1 | Регистрация RU, EN, VI (по алиасу на язык) | `sign-up/email` 200 `{ok:true}`, пользователь с `email_verified=0` |
| 2 | Письмо через Resend | Письмо на нужном языке от `Tallshift <no-reply@tallshift.com>`, ссылка `/{locale}/auth/verify-email` |
| 3 | Вход до подтверждения | 403 `EMAIL_NOT_VERIFIED` |
| 4 | Подтверждение | `verify-email` 200; `email_verified=1`. Повторное открытие той же ссылки — 400 `INVALID_TOKEN` |
| 5 | Неверный пароль и вход | 401 `INVALID_CREDENTIALS`; затем 200, кабинет показывает адрес, одна сессия в D1 |
| 6 | Второе устройство и выход с текущего | После «Выйти» сессия первого устройства удалена, второе остаётся |
| 7 | Выход со всех устройств | `revoke-sessions` 200; сессий 0, `auth_version` +1; второе устройство после обновления вышло |
| 8 | Повторная регистрация того же адреса | 200 без раскрытия; нового письма нет; новый пароль не входит, старый входит |
| 9 | Запрос сброса (EN и VI) | Письма на нужном языке, ссылка `/{locale}/auth/reset-password` |
| 10 | Сброс пароля | 200; сессии удалены, `auth_version` +1; старый пароль 401, новый 200; повторная ссылка 400 |
| 11 | Просроченная ссылка | Ссылка сброса старше 1 часа даёт 400. Требует ожидания; иначе отмечается как непроверенная |
| 12 | Пересылка support@, tallback@, mt@ (если Max Tall согласится) | Письмо с другого ящика приходит в Gmail |

Ограничения сервера, которые учитываются: не больше 10 входов и 5 регистраций или сбросов на адрес за 10 минут. Тестовые аккаунты останутся в production D1; удаление — отдельная запись в базу, только по «да» Max Tall.

## Решения и действия для Max Tall

1. **Деплой исправления заглушки.** Сначала staging, потом production; push в `main` запускает сборки Cloudflare. Демо-серверы пересобирать не нужно: их бандлы не меняются. После деплоя повторить `verify-live-demos.mjs` и проверить SSR главной.
2. **Cloudflare Web Analytics:** оставить и упомянуть в условиях и приватности или выключить.
3. **Задача Б отложена.** Нужно решение по вопросу 1 roadmap: оставить вход или временно выключить его до страницы о данных и удаления аккаунта. После решения — сквозная проверка по плану выше. Адреса, среда и судьба тестовых аккаунтов уже решены.
4. **A001:** исправить разрыв подписи в рецепте — передать сессии рецептов, и после деплоя повторить `verify-live-demos.mjs`, где этот дефект уже ловится.
5. **Временные 503 на staging и выключенные журналы Workers:** при следующем сбое скрипт сохранит код Cloudflare. Постоянное наблюдение — BETA-03 в roadmap.
6. Отдельные задачи для других зон:
   - экран «Загружаем страницу…» и частично нестилизованный SSR на медленной сети — фронтенд;
   - запрос сессии при выключенной авторизации на staging — платформа;
   - начальная высота превью на телефоне;
   - `<noscript>` для Next-приложения — нужны тексты на трёх языках и проверка копирайтера;
   - `id`/`name` поля длительности;
   - дубли `Permissions-Policy`.
