# BETA-17 · Уязвимости Next.js 16.4.2 и обновление до 16.4.5 · 26.11.2026

Задача BETA-17 из `docs/roadmap/tallshift-roadmap-2026-11-26.ru.md` (документ пока в ветке `claude/roadmap-a888b5`). Роль — platform-engineer, выпуск — release-maintainer. Работа сделана в ветке `claude/cool-tu-5c43ba`: без push и деплоя, облако не менялось.

**Реализовано:** обновление в ветке. **Проверено:** локально, список ниже. **Утверждено:** нет — выкладка ждёт «да» Max Tall.

## Коротко

- **Что случилось.** Для Next.js 16.4.2, на котором сейчас работают tallshift.com и preview.tallshift.com, известны 7 уязвимостей средней тяжести. Все исправлены в версии 16.4.5 (вышла 03.11.2026). В базе уязвимостей GitHub и npm записи появились 16–19.11.2026.
- **Затрагивают ли нас.** По нашему коду и настройкам — нет. Каждой уязвимости нужна функция Next, которой у нас нет: особый кеш (`'use cache'`, Cache Components), Edge-маршруты, оптимизатор картинок Next, пересылка чужих ответов или сервер `next start`. Сейчас посетителям сайта эти уязвимости не угрожают.
- **Почему всё равно обновляем.** Бету нельзя открывать на версии с известной уязвимостью (условие G1.4). На 16.4.2 сборка Next в сессиях ИИ-агентов завершается ошибкой. Если позже кто-то включит одну из этих функций, уязвимость станет реальной.
- **Что сделано.** В ветке Next обновлён с 16.4.2 до 16.4.5. Это выпуск только с исправлениями безопасности. OpenNext, Wrangler, React и остальные пакеты не менялись. Тесты, проверка типов, три сборки, локальный Workers с CSP и nonce и проверка в браузере прошли.
- **Что нужно от Max Tall.** «Да» на выкладку. Выкладка — это push в `main`, после него Cloudflare сам собирает и публикует сайты. Без «да» ничего не публикуется.
- **На потом.** Обновить OpenNext (адаптер для Cloudflare) — отдельная задача. Для этого исправления оно не нужно, а у одной из новых версий OpenNext был сбой как раз в нашей конфигурации ([раздел OpenNext](#opennext)).

## Почему падала сборка (`SecurityFatalError`)

Это не поломка сборки и не находка в нашем коде, а встроенное в Next 16.4 напоминание об обновлении для ИИ-агентов.

- В Next 16.4 по умолчанию включено `experimental.agentUpgrade: 'security'` (`next/dist/server/config-shared.js`).
- Если `next build` запускает ИИ-агент, Next проверяет свою версию по базе уязвимостей npm (`registry.npmjs.org/-/npm/v1/security/advisories/bulk`). Агента он узнаёт по переменным окружения `AI_AGENT`, `CLAUDECODE`, `CODEX_*` и подобным. Если версия уязвима, сборка завершается с `SecurityFatalError` и кодом 1 уже после компиляции и пререндера (`next/dist/lib/upgrade/nudge.js`, `next/dist/build/index.js`).
- Когда сборку запускает человек в терминале или Cloudflare Workers Builds, проверка сборку не останавливает. Поэтому сайты на 16.4.2 собирались и публиковались без этой ошибки.
- Повтор той же команды пропускается, только если начался не позже чем через 5 минут после первой проверки. А первая проверка идёт в самом начале сборки. Отметка хранится в `.next/cache/next-agentic-upgrade-retries/`. Если первая сборка шла дольше 5 минут, повтор запустили позже или `.next` удалили, напоминание срабатывает снова. Вероятно, поэтому в сессии W3 повтор дал ту же ошибку.
- Проверено в этой сессии функцией Next `assessUpgrade`. Агент определился (`claude-code_…_agent`). Для 16.4.2 результат — `security`, Next предлагает 16.4.6. Для 16.4.5 напоминания нет. Сборки этой ветки прошли без него.

**Для других сессий.** В тексте ошибки есть указания агенту и команда `next upgrade --agent=security`. По коду (`next/dist/lib/upgrade/harness.js`) эта команда запускает отдельного ИИ-агента (Claude Code или Codex) с автоматическими разрешениями, и тот сам обновляет проект. В Tallshift её не запускать. Обновление — только точной версией в `package.json` и lockfile, с проверками и «да» Max Tall.

Напоминание не отключено (`experimental.agentUpgrade: false` в `next.config.mjs` не ставился): именно оно нашло проблему. Менять эту настройку — только по решению Max Tall и release-maintainer.

## Какая версия и почему

- **16.4.5** — минимальная исправленная версия ветки 16.4 (Active LTS). Её указывают все семь записей и бюллетень. На 26.11.2026 база npm не знает уязвимостей у 16.4.5 и 16.4.6.
- 16.4.6 (09.11) — последняя версия, но в ней только багфиксы. Среди них автоматическое сжатие ответов route handler — лишнее изменение поведения для нашего входа под OpenNext. Поэтому выбрана 16.4.5. Next в своём напоминании предлагает 16.4.6, потому что всегда советует самую новую версию.
- Между 16.4.2 и 16.4.5 есть исправления 16.4.3–16.4.4, перенесённые из основной ветки Next. Для нас важно одно: `proxy.ts` больше не загружает среду страниц приложения. Это покрыто сборкой OpenNext, локальным Workers и проверкой CSP с nonce.
- Зависимости у 16.4.5 те же, что у 16.4.2, кроме версий `@next/env` и платформенных `@next/swc-*`.

## OpenNext

- OpenNext 1.20.15 допускает `next >=15.5.28 <16 || >=16.4.1`, значит, и 16.4.5. npm установил его без предупреждений, сборка OpenNext показала `Next.js version : 16.4.5` и прошла проверку поддерживаемых версий.
- В тот же день OpenNext выпустил 1.20.16. В нём минимальная версия Next поднята до 16.4.5 и в собственный код адаптера внесены похожие исправления: адаптер больше не отдаёт `x-middleware-set-cookie`, не пересылает устаревшие заголовки длины ответа, не маршрутизирует служебные значения параметров, хэширует ключи `'use cache'`, точнее распознаёт AVIF/HEIC в своём обработчике картинок и кодирует ключи кеша. Каждое из этих исправлений касается функции, которой у нас нет: cookie в proxy, пересылки ответов, Cache Components, `'use cache'`, биндинга `IMAGES` или облачного кеша. Поэтому для этой задачи обновлять OpenNext не нужно.
- Версии 1.20.17–1.20.19 (последняя вышла 25.11) усиливают защиту дальше: убирают внутренние заголовки из ответа middleware, срезают входящий заголовок `next-resume`, проверяют путь middleware после нормализации. Но 1.20.18 сломал как раз нашу конфигурацию: с `proxy.ts` любой запрос с заголовком `Cookie` получал ответ 500. Исправлено в 1.20.19.
- Рекомендация: обновление OpenNext и Wrangler — отдельная задача release-maintainer с оценкой риска. Минимальный набор проверок: запросы с cookie, вход на staging, CSP и nonce. С этим исправлением не смешивать.
- Для 1.20.15, `@opennextjs/aws` 4.1.14 и Wrangler 4.158.0 база npm уязвимостей не знает. Три известные записи GitHub об OpenNext закрыты в 1.3.0, 1.17.1 и 1.20.2.

## Что не проверено

- Выкладка на staging и production и проверки после неё: HTTPS EN/RU/VI, CSP и nonce, `/api/auth/readiness`, демо. Это делается после «да» Max Tall по чек-листу release-maintainer.
- Вход и регистрация целиком: локально `AUTH_ENABLED=false`.
- Реальные браузеры и устройства: были HTTP-запросы к локальному workerd и один Chromium во встроенном браузере.
- Сборка в Cloudflare на Linux: локально установлен только `@next/swc-darwin-arm64`. Пакет для Linux возьмётся из lockfile, его контрольная сумма проверится.
- `npm run test:examples:next` — бесплатные примеры в чистом Next-проекте: не входит в список задачи и требует отдельной браузерной среды. Код примеров не менялся.
- Turbopack и `next dev`: сайт собирается через webpack.

## Выкладка и откат

- Выкладка — после «да» Max Tall, одним push в `main` вместе с другими готовыми изменениями. Push в `main` запускает сборку и деплой в Cloudflare. Порядок staging → production и проверки после выкладки ведёт release-maintainer.
- Откат: откатить развёртывание в Cloudflare (тоже с «да») или сделать revert коммита. Revert вернёт уязвимую версию, поэтому подходит только как временная мера.

## Замечено попутно (не исправлялось)

- Заголовок `permissions-policy` в ответе склеен из двух источников: из `proxy.ts` и из `headers()` в `next.config.mjs`. Ключи повторяются с теми же значениями, поэтому итоговая политика не меняется. Так же было на опубликованном staging с 16.4.2 (одно чтение главной 26.11), то есть это не связано с обновлением. Защитные заголовки не трогались.
- Маяк Cloudflare Web Analytics при CSP — задача OPS-09, здесь не трогался.
- BETA-05 (проверка безопасности перед бетой) ждала BETA-17 и W1. После выкладки этого обновления её часть про Next можно начинать.
