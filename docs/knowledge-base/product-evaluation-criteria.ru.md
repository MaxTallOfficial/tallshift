# Критерии оценки предложений и готовности · 26.11.2026

Зачем этот документ: чтобы в Tallshift попадало только то, что решает реальную задачу пользователя, и чтобы продукт не превратился в «нейрослоп» — набор красивых, но ненужных или нечестных фич. Документ обязателен для всех агентов команды ([состав](agent-team.ru.md)) и для любого нового предложения, от фичи до изменения текста на главной.

Решение о scope, ценах, условиях и внешних действиях принимает Max Tall. Критерии помогают ему решать быстрее, но не заменяют его решение.

## 1. Что такое Tallshift (опорная точка для любых оценок)

Библиотека React-блоков, элементов интерфейса и анимаций. Пользователь выбирает пример, проверяет его в работе, настраивает и получает **локальный исходный код** + запрос для ИИ + инструкцию для своего существующего проекта на Next.js или Vite. После интеграции наш сервис не нужен.

ЦА — 16–45 лет: разработчики и люди, которые собирают сайт с ИИ-редактором. Они не знают нашего жаргона.

Обещание продукта: **готовый, честный, переносимый код, который выглядит хорошо и работает сразу.** Всё, что не усиливает это обещание, требует особенно сильного обоснования.

## 2. Жёсткие стоп-условия

Если хоть одно условие срабатывает — предложение не идёт в работу, пока его не переформулируют или пока Max Tall явно не решит иначе.

| # | Стоп-условие | Пример слопа |
| --- | --- | --- |
| S1 | Нельзя назвать конкретного пользователя и его задачу одним предложением | «Добавим AI-ассистента, это тренд» |
| S2 | Нечем подтвердить, что проблема существует: ни данных, ни наблюдения, ни прямого запроса Max Tall, ни требования ТЗ | «Пользователям наверняка понравится» |
| S3 | Противоречит обещанию продукта или scope v1.0 (встроенный LLM, маркетплейс, подписка, seats, cloud-генерация, no-code конструктор) | «Сделаем визуальный редактор страниц» |
| S4 | Требует выдумать данные: цены, налоги, отзывы, метрики, количество пользователей, юридические условия, курс валют | «Покажем “1000+ разработчиков уже с нами”» |
| S5 | Выдаёт запланированное за готовое или обещает то, чего нет (оплата, позиции каталога, аккаунт с покупками) | Карточка платного набора с кнопкой «Купить», которая никуда не ведёт |
| S6 | Ломает утверждённую систему: палитру, Manrope, иконки Hugeicons, общие компоненты, правила фокуса и размеров | «Новый яркий градиент для акций» |
| S7 | Ослабляет безопасность или приватность: CSP, секреты, проверка прав на сервере, данные пользователя | «Временно отключим CSP, чтобы заработало демо» |
| S8 | Нельзя описать, как проверим, что стало лучше | «Улучшим общее впечатление» |

## 3. Балльная оценка

Каждое предложение, прошедшее стоп-условия, оценивается по шкале 0–3 (0 — нет, 1 — слабо, 2 — да, 3 — сильно, с доказательством).

| Критерий | Вес | Вопрос |
| --- | --- | --- |
| Ценность для пользователя | ×3 | Насколько это ускоряет путь «нашёл → проверил → вставил в проект → работает»? |
| Доказательство | ×3 | Насколько надёжно основание: прямой запрос Max Tall / требование ТЗ / наблюдение за людьми / наша догадка? |
| Связь с выручкой или запуском | ×2 | Приближает ли к бесплатной бете и первым продажам из roadmap? |
| Честность и ясность | ×2 | Пользователь сразу понимает, что это и что произойдёт? Нет ли обещаний без покрытия? |
| Переиспользование | ×1 | Строится на существующих компонентах и данных, а не плодит параллельные системы? |
| Стоимость и риск (обратная шкала) | ×2 | 3 — дёшево и обратимо, 0 — дорого, рискованно или необратимо |

Максимум — 39 баллов.

- **≥ 28** — делаем, если есть место в текущем этапе.
- **20–27** — делаем только после уточнения слабого критерия или в следующем этапе.
- **< 20** — не делаем. Записываем в «отклонённые» с причиной, чтобы не возвращаться к той же идее.
- Если «Ценность» или «Доказательство» = 0 — не делаем при любой сумме.

Оценку ставит автор предложения, перепроверяет `product-lead`, а для заметных изменений интерфейса — `user-critic` в отдельной сессии.

## 4. Признаки слопа (чек-лист для ревью)

Если видишь три и больше — остановись и пересмотри.

- Фича описана через технологию («на базе ИИ», «умный», «динамический»), а не через результат для человека.
- Текст гладкий, но после прочтения непонятно, что нажать и что произойдёт.
- Декор без функции: свечения, градиенты, бейджи «New», «Popular», «Hot» без данных, конфетти.
- Числа и социальные доказательства без источника.
- Новый экран или раздел там, где хватило бы подписи рядом с полем.
- Меню или popover, в котором только подсказка.
- Иллюстрация обещает функцию, которой нет.
- Одинаковые карточки для разных по смыслу вещей.
- Решение дублирует уже существующий компонент «чуть по-другому».
- Отчёт о работе с цифрами, которые нельзя воспроизвести, или с «всё проверено» без списка проверок.
- Предложение не упоминает, что будет с RU/VI, мобильной шириной и клавиатурой.

## 5. Определение готовности (Definition of Done)

Работа считается сделанной, только когда выполнено всё, что к ней относится, и это записано.

**Для любой задачи**
- Есть ссылка на карточку предложения или задачу из roadmap.
- `git diff --check` чистый; изменения в своей ветке, без случайных файлов, секретов и сгенерированных сборок.
- Результат записан в `docs/knowledge-base`: что реализовано, что проверено (команда, среда, число случаев, итог), что не проверено. Утверждено — только если Max Tall сказал это.

**Для кода**
- `node --test --test-concurrency=2 tests/*.test.ts` и `npm run build` из `prototype` проходят; для платформы — `npx tsc --noEmit -p tsconfig.next.json` и `npm run build:cf`.
- Новые тесты на новое поведение, включая ошибки.

**Для интерфейса**
- Все состояния: загрузка, пусто, ошибка, недоступно, успех, длинный текст.
- 320 / 768 / 1440 px, RU / EN / VI, клавиатура, reduced motion, forced colors — проверено в реальном браузере после финального текста.
- Проверка копирайтера записана в [журнал](copy-review.ru.md).
- Защищённый `npm run check:design` — результат записан честно.
- Нет самодельных SVG, CSS-стрелок, текстовых глифов и нативных disclosure-маркеров.

**Для позиции каталога**
- Настоящее демо, точные исходники, запрос для ИИ, инструкция, manifest, SHA-256 и ZIP совпадают с одними настройками; пример работает в чистом Next.js и Vite проекте.

**Для облака и денег**
- Сначала staging, потом production, каждое внешнее действие — с явным «да» Max Tall.
- Сквозной сценарий проверен по-настоящему, а не на подменённых ответах; подменённые проверки так и названы.

## 6. Шаблон карточки предложения

```md
### <Название по сути, без жаргона>

- Автор / дата:
- Пользователь и задача (одно предложение):
- Доказательство (ссылка на ТЗ, запрос Max Tall, наблюдение, данные):
- Что меняется для пользователя (до → после):
- Как проверим, что стало лучше:
- Затронутые страницы / файлы / роли агентов:
- Стоимость и риски, обратимость:
- Стоп-условия S1–S8: пройдены / какое сработало
- Баллы: ценность _ ×3, доказательство _ ×3, запуск _ ×2, ясность _ ×2, переиспользование _ ×1, стоимость _ ×2 = _ / 39
- Решение: делаем / уточнить / не делаем — кто решил
```

Отклонённые предложения с причиной добавлять в конец roadmap, чтобы не обсуждать их повторно без новых данных.
