## 1. Что уже решено, а что предлагается

**Подтверждено пользователем:** публичный сервис для разработчиков и вайбкодеров; основной результат — готовый код и промпт для его адаптации под существующий проект. Формат первой версии — React + TypeScript с поддержкой Next.js и Vite.

**Предлагается в этом документе:** начать с веб-интерфейсов для лендингов и продуктовых сайтов; сделать небольшой авторский каталог, настройку до экспорта и проверяемую совместимость. Сначала проверить полный сценарий на шести элементах, затем расширить библиотеку до 24.

**Технические предложения для выбранного формата:** Next.js App Router как первый поддерживаемый вариант Next.js; CSS Modules и CSS-переменные для оформления. Цены, название, язык запуска и коммерческая модель пока не утверждены.

## 2. Идея продукта

Пользователь находит выразительную секцию или эффект, подставляет свой контент и оформление, проверяет поведение и переносит выбранный результат в свой репозиторий.

Рабочее обещание: **«Выбери секцию. Подстрой под свой стиль. Забери код и инструкцию для своего AI».**

Единица продукта — комплект, в котором связаны живое демо, исходники, настройки, зависимости, инструкция и промпт. Качество определяется тем, насколько удачно элемент выглядит и насколько предсказуемо его удаётся встроить.

Главный пользовательский результат: выразительный блок уже работает в реальном проекте пользователя. Копирование текста — промежуточное действие.

## 4. Своя концепция и характер

### 4.1. Три опоры

1. **Авторские наборы, которые сочетаются.** Несколько секций объединены типографикой, сеткой, декоративными приёмами и характером движения. Пользователь видит их вместе на демонстрационной странице и может взять любую отдельно.
2. **Настройка до копирования.** Контент, акцент, фон, радиус, плотность и интенсивность движения меняются в демо. Экспорт и промпт отражают выбранное состояние.
3. **Понятный перенос в существующий проект.** В комплекте есть реальные файлы, зависимости и инструкция агенту: где искать место подключения, как использовать токены проекта и что проверить после изменений.

Карточка совместимости подтверждает обещание продукта: проверенные среды, дата проверки, размер, мобильное поведение и ограничения. Основная витрина при этом остаётся визуальной и понятной.

### 4.2. Визуальные направления

Рабочие направления для первой коллекции:

- **Product:** ясная сетка, выразительный акцент, спокойное движение для SaaS и цифровых продуктов.
- **Editorial:** крупная типографика, асимметрия, изображения и аккуратные появления для студий и портфолио.
- **Playful:** необычные формы, интерактивные детали и более активное движение для небольших брендов.

Это направления коллекций. Простая смена цвета одного блока не считается новым элементом каталога.

### 4.3. Принципы самостоятельной разработки

Создавать собственные композиции, названия, тексты, демо, промпты и исходники. Общие паттерны вроде hero, FAQ или появления при скролле служат отправной точкой для своих решений. Вести список происхождения кода, шрифтов и медиа; сохранять условия используемых библиотек. Для визуальных исследований собирать несколько разнородных референсов и фиксировать собственный замысел каждого набора.

## 6. Основной путь пользователя

**Каталог → нужный элемент → живое демо → свои настройки → код или комплект для AI → интеграция → проверка в своём проекте.**

### Сценарий A: ручная интеграция

Найти секцию по задаче, открыть демо, проверить ширины и движение, настроить контент, скачать ZIP. Выполнить команды из инструкции, добавить файлы и подключить пример использования. Все необходимые локальные helpers и ресурсы находятся в комплекте.

### Сценарий B: интеграция через AI

Выбрать среду проекта, указать желаемое место и краткие изменения. Скопировать инструкцию вместе с исходниками либо приложить ZIP. Агент изучает проект, добавляет секцию, использует доступные токены и сообщает, какие проверки выполнил. Сервис не получает доступ к репозиторию.

### Сценарий C: подбор нескольких секций

Открыть коллекцию, посмотреть секции в общем контексте, сохранить понравившиеся локально. Перенести несколько элементов с одинаковыми настройками оформления. Общие helpers при таком экспорте не должны конфликтовать.

Сценарий C в первой версии использует готовую демонстрационную страницу коллекции. Свободное перетаскивание секций и сборка собственного сайта потребуют отдельного этапа.

## 8. Страницы и интерфейс

### 8.1. Главная

Одно короткое обещание; реальное демо настройки; несколько лучших элементов; пример «демо → файлы → результат в проекте»; коллекции; ссылка в каталог. Доверие строится на доступном примере, прозрачном составе и работающем экспорте.

### 8.2. Каталог `/library`

Переключение «Секции / Компоненты / Эффекты»; поиск по названию, описанию, задаче и синонимам. Минимальные фильтры: назначение, коллекция, движение, дополнительные зависимости; при коммерческом запуске — Free/Pro.

Карточка содержит постер, название, тип, доступность и короткое описание поведения. Наведение или фокус могут запускать короткий показ, на touch доступна явная кнопка. Тяжёлые демо не запускаются одновременно во всём каталоге.

Поиск и фильтры сохраняются в URL. Фильтры разных групп объединяются условием AND, несколько значений в одной группе — OR. При нулевой выдаче видны выбранные ограничения и сброс фильтров. Для 24 элементов достаточно локального поискового индекса.

### 8.3. Элемент `/library/{slug}`

На широком экране: слева большая область демо, справа компактная панель настройки и получения результата. Ниже — инструкция, API и сведения о проверках. На телефоне — последовательные блоки без горизонтальной прокрутки всей страницы.

Управление демо: desktop/tablet/mobile, произвольная ширина контейнера при возможности, replay, light/dark для поддержанных тем, «Без движения / Мягко / Выразительно». Показать отдельный режим reduced motion. Системное уменьшение движения имеет приоритет над выбранным пресетом: «Выразительно» сохраняется как предпочтение для обычного режима, но не включает пространственные перемещения и декоративное autoplay при `prefers-reduced-motion: reduce`. Демо и экспорт соблюдают одно правило.

Основные действия: **«Забрать код»** и **«Для AI»**. Первое открывает файлы, установку и ZIP. Второе формирует инструкцию с теми же файлами и настройками. Названия инструментов могут приводиться как примеры применения; отметка «проверено с…» появляется только после реальной проверки.

У интерактивных секций демонстрационные действия обозначены. Pricing не проводит оплату, contact не отправляет письмо без подключённого обработчика. В исходнике предусмотрены props, ссылки или callbacks для настоящего действия.

### 8.4. Коллекция `/collections/{slug}`

Полная демонстрационная страница доступных секций в общем стиле, список отдельных элементов, краткое описание направления, единые значения оформления. Переход к любому элементу сохраняет выбранную палитру и движение.

### 8.5. Документация

Быстрый старт, установка в поддерживаемые среды, использование с AI, настройка оформления, доступность, лицензия, изменения версий. Инструкция начинается с минимального рабочего примера.

## 9. Настройки и соответствие экспорту

Первая версия использует ограниченный набор безопасных параметров:

- Контент: заголовки, описания, подписи, ссылки и небольшие списки, если они есть у элемента.
- Оформление: акцент, фон, текст, радиус и плотность. Шрифт по умолчанию наследуется от проекта; выбранный демо-шрифт не становится скрытой зависимостью.
- Движение: три предустановки, без произвольной временной шкалы.

Параметры имеют типы, допустимые значения и значения по умолчанию. Текст остаётся текстом, произвольные HTML/JS не принимаются. URL проверяются, недопустимые значения отклоняются с объяснением. В первой версии нет загрузки файлов пользователя: собственные медиа подключаются локально после экспорта.

Изменения применяются через props и CSS-переменные на корне элемента. Исходный код не переписывается с помощью LLM. Выбранное состояние используется демо, примером подключения, ZIP и промптом из одной модели данных.

Есть сброс к исходному варианту. Ссылка на настройки содержит только публичное состояние демо, версию элемента и версию схемы настроек; пользовательский контекст для AI в неё не включается. Перед публикацией ссылки пользователь видит, что её содержимое доступно по ссылке. Опубликованные версии исходников и схем неизменяемы и сохраняются: после выпуска 1.1 ссылка на 1.0 показывает и экспортирует 1.0 с прежними значениями по умолчанию. Если версия отозвана из-за существенного дефекта, показать причину и доступное исправление; незаметно подменять версию нельзя.

## 10. Формат кода и комплект поставки

**Выбранный исходный формат:** React + TypeScript с поддержкой Next.js и Vite. Для первой версии Next.js предлагается проверять App Router.

**Предлагаемая стилизация:** CSS Modules и CSS-переменные для оформления. Это позволяет встраивать элементы и в проекты с Tailwind без обязательного переноса глобальных настроек. Tailwind-реализация может стать отдельным проверенным форматом; конвертация агентом не считается официальной совместимостью.

CSS использовать для простых переходов и hover. Дополнительную библиотеку анимации вводить только для элементов, которым она нужна; показывать её до получения кода. Тяжёлые WebGL/3D-элементы вынести за пределы первого выпуска.

Пример комплекта:

```text
product-hero-1.0.0/
  ProductHero.tsx
  ProductHero.module.css
  Example.tsx
  config.json
  manifest.json
  README.md
  INTEGRATE.md
  LICENSE.txt
  assets/                 # только необходимые ресурсы
```

В комплекте нет внутренних импортов сервиса, несуществующего `@/lib/utils`, недоступных файлов и скрытой зависимости от его backend. Локальные helpers включаются явно. Путь для подключения ресурсов описан для обеих поддерживаемых сред.

Файлы можно просмотреть и скопировать по отдельности. ZIP содержит полный комплект. В CI подготавливаются неизменяемые исходники, ресурсы и шаблоны выбранной версии. Браузер упаковывает их вместе с текущими `config.json`, `Example.tsx` и `INTEGRATE.md`: пользовательские тексты для этого не передаются на сервер. Значения сериализуются как данные после валидации; произвольный код из ввода не исполняется. Для платных элементов исходный комплект предварительно получается через авторизованную выдачу.

Текст «Для AI» включает границы файлов и их полный текст; бинарные ресурсы передаются ZIP. Если комплект слишком велик для удобного копирования, интерфейс предлагает ZIP и короткую инструкцию, сообщает размер и ничего не обрезает молча.

В `manifest.json` фиксируются: версия формата, ID/slug, версия элемента, тип, коллекция, описание, список файлов, props и настройки, обязательные и необязательные зависимости, проверенные версии сред, особенности SSR, ресурсы и их происхождение, лицензия, сведения о доступности, ограничения, результаты и дата проверок.

Новая публикация создаёт новую версию. Ошибки исправляются с записью в changelog; изменения API описываются. В первой версии пользователь обновляет скопированные файлы вручную. Обновление библиотеки не изменяет его проект автоматически.

## 11. Промпты

Промпт предназначен для интеграции приложенного исходника и сохранения выбранного дизайна. Его сборка — обычный шаблон из manifest, настроек и введённого контекста. API модели и платные токены внутри сервиса не нужны.

Два режима: «Добавить как выбран в демо» и «Адаптировать оформление под проект». Во втором режиме можно использовать существующие цвета, шрифт, Button/Link и соглашения проекта, сохраняя композицию и выбранный характер движения. Точная визуальная копия после адаптации не обещается.

Минимальный контекст: среда Vite/Next.js, предполагаемое место подключения, желаемые изменения. Если путь неизвестен, агенту предлагается найти подходящую страницу. Контекст обрабатывается локально и не отправляется в аналитику.

Обязательные части инструкции:

1. ID и версия элемента, режим адаптации, выбранная конфигурация.
2. Полный список исходников и ресурсов, зависимости и пример использования.
3. Изучение структуры проекта, версий пакетов и его инструкций перед изменениями.
4. Конкретное действие: добавить файлы и подключить компонент в нужном месте.
5. Использование имеющихся соглашений и токенов; отсутствие ненужных изменений глобального CSS, маршрутов и зависимостей.
6. Поведение на touch, клавиатуре и reduced motion, а также граница Client Component при необходимости.
7. Проверки сборки, типов и отображения; итог с изменёнными файлами и фактически выполненными проверками.

Пример смыслового каркаса, не готовый экспорт:

> Встрой ProductHero версии 1.0.0 из приложенных файлов в существующий проект. Сначала прочитай инструкции репозитория, package.json и целевую страницу. Используй приложенный исходник и конфигурацию. Режим — адаптация к оформлению проекта: сохрани композицию, возьми текущие шрифты и токены. Подключи секцию на указанной странице. Проверь существующие зависимости до установки новых. Сохрани работу клавиатуры и системное уменьшение движения. Выполни доступные проверки проекта и сообщи результат. Ниже перечислены все файлы и выбранные параметры.

Изменения исходника и промпта публикуются как один комплект. Пользовательский текст помечается как данные контекста. Маркетинговое обещание «сработает с любым AI с первого раза» не используется.

## 12. Требования к совместимости и качеству

Каждый пункт ниже — требование к будущей реализации, а не сообщение об уже выполненном тестировании.

| Область | Критерий приёмки |
| --- | --- |
| Полнота | Чистый проект собирается по инструкции из ZIP без поиска недостающих файлов и догадок о настройках. |
| Среды | Production-сборка и TypeScript проходят в эталонных Vite и Next.js App Router. Точные версии фиксируются в manifest и lockfiles эталонов. |
| SSR | Нет обращения к browser API при импорте или серверном рендере; нет hydration warnings; client boundary обозначена. |
| Изоляция стилей | Нет глобального reset и изменений `body`; контрольные кнопка, текст и input вне корня элемента сохраняют оформление. |
| Внешние стили проекта | В одном из эталонов подключены reset и глобальные правила для заголовков, button, img и box-sizing. Элемент сохраняет структуру и работу контролов; намеренно наследуются шрифт и явно подключённые токены. Локальные базовые стили не выходят за его корень. Конфликтующие внешние `!important` фиксируются как ограничение адаптации. |
| Несколько экземпляров | Два одинаковых элемента на странице не имеют конфликтующих ID, общих несброшенных состояний и случайно общих обработчиков. |
| Размеры | При 360, 768 и 1440 px нет горизонтального переполнения страницы. Дополнительно проверяются длинный русский заголовок, удвоенный текст и 200% zoom. |
| Клавиатура | Интерактивные элементы достижимы, focus видим, порядок понятен; паттерны tabs/accordion поддерживают ожидаемое управление. |
| Доступность | Семантика, имена контролов, контраст текста в исходных пресетах; нет serious/critical ошибок автоматической проверки; ручной проход интерактивности. Изменённая пользователем палитра не получает автоматический знак соответствия. |
| Движение | Системный reduced motion имеет приоритет, включая сочетание с «Выразительно», и выключает пространственные перемещения и декоративное autoplay; смысловой контент остаётся видимым. Off выключает декоративное движение. |
| Touch | Основные действия не зависят только от hover или pointer; декоративный эффект не перекрывает нажатия. |
| Lifecycle | После unmount не остаются подписки, таймеры и animation loops; повторный mount работает корректно. |
| Видимость контента | В SSR-выводе смысловой контент виден и без JS. В Vite SPA контент не остаётся скрытым при отказе логики анимации после запуска приложения. |
| Верность экспорта | Демо и Example используют одинаковые props и значения; контрольные скриншоты совпадают с учётом фиксированного состояния анимации. |
| Настройки ZIP | Два экспорта с разными текстами и оформлением содержат соответствующие значения; каждый распакованный Example воспроизводит свой вариант. |
| Старые ссылки | После выпуска новой версии ссылка на прежнюю использует прежнюю схему, настройки и исходники; при отзыве версии отображается явное уведомление. |
| Браузеры | Проверяются выбранные на дату релиза версии Chrome, Safari и Firefox, а также Safari iOS и Chrome Android; матрица опубликована. |
| Действия | Реальные ссылки/callbacks доступны через API. Демо-формы и фиктивные данные явно описаны. |

В карточке показывать факты: «проверено в…», «требуется…», «известное ограничение…». Общая надпись «production-ready» не заменяет сведения о проверках.

Для API browser-интерактивности учитывать границу Server/Client Components, описанную в [документации Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components). Поведение reduced motion проектировать явно; [Motion](https://motion.dev/docs/react-accessibility) описывает соответствующие механизмы и примеры. CSS Modules поддерживаются в [Vite](https://vite.dev/guide/features.html#css-modules) и [Next.js](https://nextjs.org/docs/app/getting-started/css#css-modules).

## 13. Производительность и демо

В каталоге использовать постеры и отложенный запуск. На странице элемента одновременно активно одно демо; вне экрана и в скрытой вкладке декоративные циклы приостанавливаются. Ошибка демо не ломает навигацию или получение файлов; видны повтор запуска и понятное сообщение.

Демо загружается из собранного исходного комплекта, чтобы не существовало отдельной «красивой версии для витрины». Настройки передаются как валидированные данные.

Для изоляции стилей и перезапуска использовать iframe с отдельным origin для превью. Разрешения минимальны; без сессии аккаунта, доступа к платёжным данным и произвольного пользовательского кода. Обмен сообщениями ограничивается известным origin, типами и валидной схемой. Учесть рекомендации по sandbox из [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe).

Предварительные бюджеты для проверочного выпуска: каталог — до 200 KB gzip стартового JS без файлов демо; обычная CSS-секция — до 15 KB gzip добавленного JS без React и ресурсов; изображения элемента — до 500 KB суммарно в стандартном демо. Это целевые ограничения проекта, их уточняют на первом комплекте. Если нужна библиотека движения, её добавленный вес показывается отдельно и не скрывается из общего результата.

Фиксировать инструмент и условия измерения. В публичной версии целиться в LCP ≤2,5 с, INP ≤200 мс и CLS ≤0,1 на 75-м перцентиле реальных визитов отдельно для mobile и desktop при достаточных данных, согласно ориентирам [Core Web Vitals](https://web.dev/articles/vitals). До этого использовать воспроизводимые лабораторные замеры без заявления о полевых результатах.

## 14. Техническая организация

Предлагаемая архитектура: сайт каталога и документации на Next.js + TypeScript; элементы и их manifest — в Git; статические ресурсы — в объектном хранилище/CDN; сборка превью и базовых комплектов — из тех же исходников в CI. Панель настроек, формирование пользовательского Example, промпта и итогового ZIP работают в браузере по правилам раздела 10.

В бесплатном проверочном выпуске база данных и аккаунты не нужны. Избранное публичного каталога можно хранить в localStorage. Каталог не сканирует репозитории и не требует ключей AI-инструментов.

Пример структуры будущего проекта:

```text
app/                     # каталог, страницы, документация
content/items/           # manifest, исходники и инструкции элементов
content/collections/     # описание наборов и порядок секций
preview/                 # сборка демонстраций
fixtures/vite/           # эталон интеграции
fixtures/next/           # эталон SSR и интеграции
scripts/                 # валидация, упаковка, индекс каталога
```

Публичный индекс содержит метаданные и ссылки на демо. Если появится платный доступ, выдача исходников и ZIP проверяет права на сервере. Платные исходники не должны попадать в публичный JSON, HTML страницы или общедоступный source map. При этом код интерактивного демо исполняется у посетителя: абсолютная защита от восстановления его поведения не является обещанием продукта.

## 15. Выпуск нового контента

Поток: собственный визуальный замысел → исходники → схема настроек → пример → ресурсы и происхождение → проверки → демо → экспорт и промпт → публикация версии.

Контент управляется через Git и review. Отдельная административная CMS для первой версии не нужна. Каждый новый элемент автоматически попадает в каталог после проверки manifest; ручное редактирование нескольких несвязанных списков не требуется.

В CI блокировать публикацию при отсутствующем файле, ошибке типов/сборки, неизвестной зависимости, неполном комплекте ресурсов, несовпадении конфигурации и экспорта, невалидном manifest или отсутствующей лицензии. Визуальная и ручная проверка интерактивности подтверждаются отдельной отметкой с датой.

## 16. Коммерческая модель — решение после проверки ценности

Публичность не требует немедленной оплаты. Рекомендуется сначала открыть шесть бесплатных примеров, проверить успешность интеграции и интерес к следующим наборам.

Для первого платного предложения рассмотреть **покупку конкретного авторского набора**: состав известен, скачанная версия остаётся доступной для использования, срок получения новых версий указан до оплаты. Возможный вариант — 12 месяцев обновлений купленного набора. Бессрочная подписка на все будущие работы не предполагается автоматически.

Цену не фиксировать по одному конкуренту. Сначала проверить несколько ценовых предложений на интервью и реальных намерениях купить. Бесплатные примеры должны демонстрировать весь путь, включая исходники и промпт. Демо платных элементов доступны до покупки.

Коммерческий этап имеет отдельную приёмку:

- Понятные состав набора, сумма, валюта, налоги/сборы и условия обновлений до перехода к оплате.
- Аккаунт для восстановления покупок, выдача прав только по подтверждённому сервером событию провайдера.
- Проверка подписи webhook, идемпотентность повторных событий, обработка задержки, неуспеха, возврата и отзыва доступа к новым скачиваниям.
- Уже выданные права использования скачанной версии описаны отдельно от доступа к последующим загрузкам.
- Закрытые endpoints выдачи проверяют владельца покупки; прямой URL ZIP не обходит авторизацию.
- Покупка восстанавливается после входа; ошибки оплаты и поддержки имеют понятный маршрут.

Платёжный провайдер выбирается после уточнения страны регистрации продавца и целевых покупателей. Лицензионные условия, политика возвратов и работа с персональными данными оформляются до приёма платежей с учётом выбранных рынков.

Рабочая продуктовая политика лицензии: разрешить использование и изменение в собственных и клиентских конечных проектах; условия распространения исходных наборов, ресурсов и промптов оформить явно. Это требования к будущим условиям, а не готовый юридический текст.

## 17. Метрики и проверка гипотез

Основная гипотеза: авторский дизайн, настройки и комплект для AI сокращают путь до работающего блока в чужом проекте.

Провести 10 наблюдаемых пробных интеграций: пять вручную, пять с AI; распределить между Vite и Next.js. Участники работают в существующих проектах и берут элемент, соответствующий реальной задаче. Зафиксировать начальный уровень участника, время, ошибки, помощь автора и итог.

Предварительный критерий продолжения: минимум восемь успешных интеграций из десяти без исправления библиотечных исходников автором; медиана времени до рабочего результата — до 15 минут. Эти числа — порог эксперимента, не прогноз и не маркетинговое обещание. При провале выяснить причину до расширения каталога.

События продукта: открытие элемента, запуск демо, изменение настройки, успешное копирование, скачивание ZIP, возврат к элементу, добровольная оценка интеграции. Для анализа достаточно ID/версии элемента и типа действия. Тексты, введённый код, контекст проекта и содержимое clipboard в аналитику не отправляются.

Копирование не считается доказанной установкой. Завершение интеграции измеряется наблюдаемым тестом или добровольным подтверждением. Конверсию в оплату и повторные покупки оценивать после появления платного предложения.

## 19. Основные риски и решения

| Риск | Решение |
| --- | --- |
| Выглядит как ещё один каталог | Сильные авторские наборы, наглядная настройка, показ результата в реальном проекте |
| Много эффектов, мало полезных секций | Первые три секции решают связный сценарий лендинга; контент проверяется на задачах пользователей |
| Демо и скачанный код отличаются | Одна модель настроек, общий исходник, проверка экспорта |
| AI переписывает элемент и теряет дизайн | Приложенный код, два явных режима, ограничения адаптации и чек-лист проверки |
| Стили портят сайт пользователя | CSS Modules, локальные переменные и проверка на странице с контрольными элементами |
| Каталог перегружает устройство | Постеры, одно активное демо, остановка фоновых циклов |
| Поддержка множества стеков тормозит выпуск | Один проверенный формат; остальные добавляются по подтверждённому спросу |
| Обещаны слишком большие обновления | Продавать понятный состав и условия, наращивать контент после проверки процесса |
| У пользователя нестандартный проект | Явная матрица поддержки, ограничения, инструкция адаптации, канал сообщения об ошибке |

## 20. Что нужно выбрать для следующей редакции

1. **Стилизация и матрица поддержки:** формат React + TypeScript, Next.js/Vite уже выбран. Уточнить CSS Modules или Tailwind и зафиксировать проверяемые версии; рабочее предложение — CSS Modules и Next.js App Router.
2. **Первое визуальное направление:** Product как наиболее универсальное; Editorial или Playful — если хочется сильнее выразить характер с первого выпуска.
3. **Язык:** предложение — английский интерфейс и документация при международном запуске; русские промпты и документацию добавлять как отдельный проверенный перевод. Альтернатива — русскоязычная бета для быстрого сбора обратной связи.
4. **Монетизация:** бесплатный проверочный выпуск; затем наборы, единый доступ к библиотеке или продолжение бесплатной модели.
5. **Название и бренд:** отдельная короткая работа после выбора визуального характера и аудитории запуска.

Следующий конкретный артефакт после обсуждения — схема каталога и страницы элемента с одним оригинальным hero, на котором проверяется весь путь до экспорта.
