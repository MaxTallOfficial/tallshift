# Серверная реализация покупки и доступа: дополнение к ТЗ

26.10.2026. Требования к будущему production backend. Локальная дизайн-система и её модели представления не являются авторизацией, оплатой или хранилищем прав. Используются маршруты из [инженерного ТЗ](engineering-and-security.ru.md), состав и расчёт из [контракта тарифов](pricing-final-contract.ru.md).

## Источник данных для интерфейса

Адаптер кабинета получает проверенные сервером права по item ID, покрытие функциональных обновлений, состояние заказа и доступность выдачи. `deriveAccessState` и `summarizeCoverage` в библиотеке только переводят эти сведения в представление; изменение их аргументов в браузере не должно открывать приватный endpoint.

Состояния проверки: loading / error / verified. До verified нельзя показывать отсутствие покупки как установленный факт или предлагать повторную оплату. Отдельно различаются pending payment, paid awaiting access и complete. Доступные исходники, частичное владение, срок обновлений и сбой выдачи не подменяют друг друга. Для каждого поля определены доступное сообщение, действие, безопасный повтор и возврат фокуса.

Для каждой действующей покупки сервер возвращает список материалов и дату окончания функциональных обновлений. UI группирует материалы по дате, при пересечении действующих оснований берёт наиболее позднюю дату; неизвестную дату не угадывает. Даты в формате YYYY-MM-DD включают указанный день по UTC; API может хранить точные timestamps, но должен одинаково преобразовывать их на сервере и клиенте. В расчёт не входят отозванные/возвращённые основания.

## Переходы и идемпотентность

| Триггер | Обязательное поведение сервера и UI | Приёмка |
| --- | --- | --- |
| Создание quote | Session, CSRF, Origin; проверка актуальных прав, готовности, offer revision и валюты; server-side missing IDs и best-eligible сумма. Срок действия и привязка к user ID | Подменённые item IDs, суммы, чужой/просроченный quote отклоняются. Пользователь видит новую сводку до оплаты |
| Создание checkout session | Идемпотентный ключ на намерение покупки, принадлежащий пользователю quote. Одинаковый запрос возвращает тот же результат; другой payload с тем же ключом даёт конфликт | Двойной клик/повтор после таймаута не создаёт второй checkout или charge |
| Webhook | Проверка raw signature, merchant, mode, currency, transaction и суммы; durable receipt до ответа 2xx. Уникальный provider event ID | Подделки и несовпадения не выдают права; дубликаты не добавляют второй grant |
| Оплата подтверждена | Заказ paid фиксируется независимо от доставки уведомления браузеру. Grant создаётся транзакционно/через надёжную очередь и сверку, только на оплаченные missing IDs | Crash после receipt и до grant commit восстанавливается reconcile без повторной оплаты; UI «Оплата получена, готовим доступ» |
| Пользователь закрыл checkout | Локальное закрытие окна не отменяет заказ на сервере | Поздний paid webhook переводит заказ в paid; устаревшее pending/cancelled событие не понижает подтверждённый статус |
| Refund/chargeback | Отзыв оснований конкретного заказа; пересчёт по каждому item, с сохранением других действующих покупок | Возврат Product после доплаты оставляет 17/23; возврат заказа доплаты отзывает только его 17. Повтор события не меняет результат |
| Владение изменилось между quote и оплатой | До checkout — пересчёт и подтверждение. Если провайдер уже принял деньги — сверка оплаченного snapshot и текущих прав | Без нового списания «разницы» и без автоматической выдачи неоплаченного расширенного состава. Переплата/двойная покупка получает отдельное разрешение через провайдера/поддержку с видимым статусом |
| Выдача архива | Авторизованный поток, проверка user ID, прав по item и статуса версии на каждом запросе, private/no-store | Чужой или отозванный доступ не выдаёт байты; временный 503 не удаляет владение. Повтор скачивания не создаёт заказ |
| Окончание обновлений | Сохраняется право использования полученной редакции; доступ к функциональным релизам определяется датой покрытия | Повторный вход не предлагает купить уже принадлежащий код. Security remediation и безопасная замена по инженерному ТЗ |

Не все провайдеры гарантируют одинаковый порядок событий. Адаптер хранит историю, получает авторитетное текущее состояние провайдера при спорном переходе и учитывает возвраты отдельно от подтверждения оплаты. Return URL, query-параметр paid=true или клиентский callback не подтверждают оплату.

## Потеря доступа к аккаунту и удаление

Покупка принадлежит стабильному user ID; email плательщика и email входа могут различаться. Смена email проходит проверку владельца и не переносит заказ сама по себе. Восстановление требует идентификации заказа и аккаунта, подтверждения личности через утверждённый auth/support процесс, журналирования и отзыва прежней привязки. Один введённый адрес/скриншот оплаты не выдаёт права.

При удалении аккаунта отзываются сессии, объясняются допустимые исключения для бухгалтерских записей и резервных копий. Политика хранения, сроки удаления и возможное восстановление покупок после удаления согласуются с продавцом/MoR до запуска. До этого UI не обещает ни безусловное вечное хранение данных, ни автоматическое восстановление удалённого аккаунта.

## Честная граница готовности

Сейчас в репозитории реализованы локальные расчёты, модели состояний и визуальные сценарии. Нет production-сессий, merchant adapter, подписанных webhook, durable ledger, приватного object storage и серверной потоковой выдачи Pro. Эти работы обязательны перед продажей; настройки commerce_enabled=false не меняются. Для их запуска нужны выбранный продавец/провайдер, условия и инфраструктура. Применять демонстрационный buyer scenario как источник реальных прав запрещено.
